# Zoe「钱多多」体验优化路线图

> 目标：降低日常记账的操作成本，并把流水数据转化为可信、可理解、可行动的个人财务信息。本文是实现基线，后续每次迭代都应补充变更、测试和验收结果。

## 一、产品判断

当前实现已经具备值得保留的基础：本地离线记账、金额按分存储、收入/支出/转账分离、分类最近账户建议、连续记账与复制、全局流水搜索、账户余额、六个月收支趋势，以及统计到分类流水的下钻。优化不应推翻这些能力。

当前主要体验风险不是功能数量不足，而是信息组织与用户决策目标尚未完全对齐：

1. 首页同时承担流水浏览、期间切换、收支摘要、分类排行和多个入口，首次使用者不一定能迅速判断“我现在财务状况如何、下一步做什么”。
2. 记账编辑器包含类型、金额、账户、分类、日期、备注等完整能力；虽已有快捷分类和折叠详情，但新手仍可能把可选信息误认为必填步骤。
3. 账户页以账户余额列表为主，用户需要自行理解“账户余额合计”和“本期可支配现金流”不是同一个概念。
4. 统计页目前重点展示六个月收入/支出和分类构成；尚缺少对比基准、趋势解释和异常消费提示，数据展示还没有完全转化为行动建议。
5. 产品设计文档中曾规划预算、家庭成员、共享同步等能力，但当前可运行实现明确是本地单机账本。不能把未实现的家庭账本、预算或同步入口伪装成现有能力。

## 二、体验设计原则

- 先完成记录，再完善信息：金额与收支类型优先；分类、账户按实际业务需要呈现；日期和备注默认为可选。
- 默认值必须可解释：账户建议应标注“按分类建议”或“最近使用”，且用户手动选择后不得被静默覆盖。
- 财务口径始终一致：收入、支出、转账严格区分；转账不计入收入/支出；账户余额、期间结余、净资产不可混用。
- 分析必须可下钻：任何分类金额或趋势结论都能进入对应流水；明确当前筛选范围。
- 逐步披露而非堆叠功能：高频动作直接展示，低频字段折叠；避免新增一级入口。
- 安全优先：删除前确认、失败时保留草稿、金额以整数分计算、所有优化不破坏既有数据库和历史流水。
- 跨平台一致：优先在 commonMain 实现；Android 与桌面共用规则，布局可按窗口尺寸调整。

## 三、目标信息架构

保持当前少量页面与现有导航，不引入新的复杂主导航：

- 流水首页：期间选择 + 本期关键数字 + 分类重点 + 按日期排列的流水 + 固定“记一笔”。
- 记账编辑器：收支类型与金额 → 分类与账户 → 可选日期/备注 → 保存；让默认路径尽可能短。
- 统计：六个月趋势 → 选中月份收支摘要 → 分类构成 → 对应明细。
- 账户：账户余额列表 + 合计余额；清晰说明该合计是当前账户余额合计，而非当月结余。
- 搜索/筛选：保留跨日期检索与组合关键词；让筛选状态可见、可清除。

## 四、分阶段实施

### P0：低风险、高收益（优先）
- 统一关键财务术语：本期收入、本期支出、期间结余、账户余额合计。
- 明确当前期间范围和筛选状态，减少“数字到底统计哪段时间”的疑问。
- 为首页、统计、账户页补充简短口径说明与空状态指引。
- 检查编辑器默认账户、最近分类、日期、复制、连续记账的状态保留与无障碍语义。
- 修正小屏/大字体下的金额截断、按钮挤压和滚动区域问题。

### P1：分析可解释性
- 在六个月趋势中强化选中月份与当前月份的区别；本月未结束时不得直接与完整历史月份作无提示比较。
- 提供上月对比金额与变化率；基数为零时显示“暂无可比基数”，不显示误导性的百分比。
- 分类排行同时展示金额与占比；占比以同一期间的总支出为分母。
- 任何新增分析指标都要能下钻到构成该指标的流水。

### P2：高频操作效率
- 基于真实使用数据评估最近分类与常用分类排序，不凭主观增加快捷入口。
- 评估记账键盘、焦点、保存反馈和连续记账的端到端操作次数。
- 评估桌面端快捷键与宽屏布局；不改变移动端单手优先的交互。

### 暂不纳入当前版本
- 家庭成员、云同步、预算管理、信用卡负债、投资收益率等需要额外数据模型或服务端能力的功能。先完成产品边界、权限、隐私、迁移与财务口径设计，再独立立项。

## 五、财务指标口径

| 指标 | 计算口径 | 不应被误解为 |
| --- | --- | --- |
| 期间收入 | 期间内收入流水金额之和 | 账户余额增加额（可能含转入） |
| 期间支出 | 期间内支出流水金额之和 | 账户余额减少额（可能含转出） |
| 期间结余 | 期间收入 - 期间支出 | 当前净资产 |
| 账户余额 | 账户期初余额 + 入账 - 出账，按账户流水规则计算 | 本月收入或本月结余 |
| 账户余额合计 | 所有有效账户余额之和 | 全部资产负债表或投资净值 |

金额必须继续使用整数分存储与计算。展示百分比时，分母为零要显式处理；展示环比时，比较期间长度和完整性必须一致。

## 六、质量门槛与验收

每个迭代必须满足：
1. :composeApp:desktopTest 通过；涉及 Android 构建或资源时同时运行 :composeApp:assembleDebug。
2. 不改变现有数据库表含义，不清除、不重置、不覆盖用户账目。
3. 收入、支出、转账的统计口径有测试覆盖；账户转账前后总余额守恒。
4. 编辑、复制、连续记账、删除确认、搜索和分类下钻的现有测试继续通过。
5. 新增界面文案使用用户语言，避免不解释的会计术语；关键操作具备可访问描述。
6. 每个 PR 说明用户问题、改动页面、财务口径、测试结果和未解决风险。

## 七、体验指标（后续可通过可用性测试采集）

- 新用户完成第一笔支出的成功率与中位耗时。
- 已有分类支出的录入步骤数（不含键盘输入）。
- 编辑/复制/连续记账误操作率。
- 搜索到目标流水的成功率与耗时。
- 用户对“期间结余”和“账户余额”含义的理解正确率。
- 统计页面分类下钻成功率。

这些指标在没有真实埋点或用户测试前不填写虚构数值。
